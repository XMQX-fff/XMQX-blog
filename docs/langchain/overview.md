# 概览与设计理念

本篇回答两个问题：LangChain 在整个生态中的位置，以及 v1 版本究竟改了什么。

## 本篇适合谁

- 正在**选型**：LangChain / LangGraph / Deep Agents 该用哪个？
- 刚升级到 **v1**：想搞清楚"1.0 到底改了什么、旧代码为什么要动"？
- 想理解官方文档背后的**设计逻辑**：为什么中间件是核心抽象？

如果你只想赶紧跑起来，可以直接跳到[快速入门](/langchain/quickstart)，

## 智能体 = 模型 + 运行框架

官方给出的核心等式为：

> **智能体 = 模型 + 运行框架。**

**名词解释：等式两边分别是什么。**
- **模型（model）**：负责推理的大脑——接收上下文，输出文本或工具调用请求；
- **运行框架（harness）**：围绕模型循环的一切外围组件——
  提示词、工具，以及任何用于塑造行为的中间件。

为什么强调这个拆分？因为**v1 最大的架构决策就是把两者解耦**：
模型可以随时换（改个字符串），框架按需组装（加中间件），
应用代码不用重写。开发者从这些基础单元出发，按用例精确组合所需能力。

```python
from langchain.agents import create_agent


def get_weather(city: str) -> str:
    """获取指定城市的天气。"""
    return f"{city} 总是阳光明媚！"


agent = create_agent(
    model="openai:gpt-5.5",
    tools=[get_weather],
    system_prompt="你是一名乐于助人的助手",
)

result = agent.invoke(
    {"messages": [{"role": "user", "content": "旧金山的天气怎么样？"}]}
)
print(result["messages"][-1].content_blocks)
# [{'type': 'text', 'text': '旧金山总是阳光明媚！（示意）', ...}]
```

`create_agent` 是一个简洁且高度可配置的运行框架。

模型采用 `"provider:model"` 形式的标识符字符串，切换提供商只需更改该字符串
与对应的 API 密钥，无需重写应用逻辑。

## 三个框架的分工

生态中三个开源框架常被混淆，官方的划分标准如下：

| 框架 | 定位 | 适用情形 |
| --- | --- | --- |
| **LangChain**（`create_agent`） | 高度可定制的运行框架 | 需要精确适配具体用例与数据 |
| **LangGraph** | 底层编排框架 | 需要组合确定性工作流与智能体工作流 |
| **Deep Agents** | 预组装的智能体运行框架 | 需要"开箱即用"的规划、文件系统、子智能体 |

三者的关系可以概括为：

- **Deep Agents** 构建于 LangChain 智能体之上，预先组装自动上下文压缩、
  虚拟文件系统与子智能体创建等能力——**开箱即用，但可改的空间收窄**；
- **LangChain** 的 `create_agent` 提供最简形态，能力按需通过中间件添加——
  **要自己搭，但每一层都能换**；
- **LangGraph** 是二者共同的底座，提供流式传输、持久执行、短期记忆与
  人在回路等能力——** LangGraph 也可以单独用来编排非智能体的确定性工作流**
  （见本博客 [LangGraph 学习笔记](/langgraph/)）。

**一句话选型**：要快用 Deep Agents，要可控用 LangChain，
要编排复杂流程用 LangGraph。三者是同一套技术的三个抽象层，各管一段。

**LangSmith** 则独立于三者之外，承担可观测性、评估与部署。
它不参与推理，只负责"看得见、测得准、发得出"。

::: note 命名变更
LangGraph Platform 已更名为 **LangSmith Deployment**。
看到旧文档里的 LangGraph Platform，指的正是它。
:::

## 核心优势

官方归纳为四项：

1. **标准模型接口**：以统一接口调用不同提供商的聊天模型与嵌入模型，
   极少的代码改动即可切换模型，保持应用可移植性。
   **解决了什么问题**：模型迭代极快，今天 GPT 明天 Claude——
   接口不标准就意味着每次升级都是一次重写。
2. **高度可配置的运行框架**：从最简的 `create_agent` 起步，通过中间件
   逐步添加能力，仅组合用例所需的功能——护栏、重试、路由、
   自定义工具策略。**解决了什么问题**：原型和生产之间隔着
   摘要、限流、审批、可观测一大堆需求，全塞进核心会让框架又胖又脆。
3. **构建在 LangGraph 之上**：可直接利用 LangGraph 的持久执行、
   人在回路、持久化等能力。**这意味着**：智能体天然可以
   "暂停等审批、崩溃后恢复、跨轮次记忆"，不用自己造。
4. **使用 LangSmith 调试**：在一个位置检查追踪记录、工具调用、
   状态转换与延迟。**这意味着**：出问题能复盘，不用靠猜。

## 设计理念

官方在"设计理念"页中列出五条核心信念：

1. LLM 卓越强大；
2. 与外部数据源结合后作用更大；
3. 应用将日益具有智能体特征；
4. 该转型仍处于非常早期；
5. **构建原型容易，构建可靠到可投产的智能体非常困难。**

**为什么第 5 条是整份文档的问题意识所在**：前四条是共识，
最后一条才是 LangChain 存在的理由——原型谁都能搭，
难的是可靠性：模型会抽风、工具会超时、上下文会爆、
人要能插手。后续的中间件、护栏、结构化输出、
人在回路等全部机制，均服务于"从原型到生产"这一跨越。

据此，LangChain 确立了两个主要方向：

- **让开发者使用最优秀的模型**：标准化模型输入输出，便于切换先进模型，
  避免供应商锁定；
- **让模型便于编排复杂流程**：模型不只生成文本，还要编排与其他数据及
  计算资源的交互，LangChain 负责工具定义与非结构化数据解析。

## 发展历程中的关键节点

以下时间线摘自官方"设计理念"页，可帮助理解当前形态的由来：

| 时间 | 事件 |
| --- | --- |
| 2022-10 | v0.0.1 发布（早于 ChatGPT 一个月），含 LLM 抽象与"链"（Chains），名称来自 Language + Chains |
| 2022-12 | 加入首批通用智能体，基于 ReAct 论文，解析模型输出的 JSON |
| 2023-01 | OpenAI 发布 Chat Completion API，输入输出由"字符串"变为"消息列表"，LangChain 随之调整 |
| 2023-03 | OpenAI 发布函数调用，改为优先使用函数调用能力，不再自行解析 JSON |
| 2023-06 | 发布闭源平台 **LangSmith**（可观测性与评估） |
| 2024-02 | **LangGraph 开源**，补足底层编排：流式传输、持久执行、短期记忆、人在回路 |
| 2024-10 | 超过单次 LLM 调用的应用首选 LangGraph；大多数链与智能体标记弃用 |
| 2025-10 | **v1.0.0**：重构全部链与智能体，统一为构建在 LangGraph 上的智能体抽象；引入标准消息内容格式 |
| 2026-03 | **Deep Agents 发布**：内置规划工具、可插拔后端的虚拟文件系统、上下文隔离的子智能体 |

读这条线注意两个转折：**2022-12 → 2023-03**（工具调用从"自己解析 JSON"
进化到"用 API 原生能力"）和 **2024-10 → 2025-10**（从"链"的抽象
收敛到"智能体"单一抽象）。后者正是 v1 全部改动的思想来源。

### v1.0 的两项关键变更

1. **统一抽象**：全部链与智能体被重构为基于 LangGraph 的智能体抽象
   （即 `create_agent`）。仍需旧版接口者可安装 `langchain-classic`。
2. **标准消息内容格式**：统一推理块、引用、服务端工具调用等复杂输出的
   表达方式，这是 `content_blocks` 属性的由来。
   细节见[模型·消息·工具 2.5 节](/langchain/components#2-5-content-与-content_blocks为什么有两个)。

## 版本选择建议

官方给出的判断依据：

- 需要**预定义工具**构建更自主的智能体 → **Deep Agents**；
- 需要**完全控制架构** → **LangChain**（`create_agent`）；
- 需要**组合确定性工作流与智能体工作流** → **LangGraph**。

## 小结

- LangChain 提供 `create_agent`：智能体 = 模型 + 运行框架。
- LangGraph 是底层编排，Deep Agents 是预组装形态，LangSmith 负责观测与评估。
- v1 的核心变更是"统一到 LangGraph 之上的智能体抽象"与"标准消息内容格式"。
- 全部设计围绕"原型易、生产难"这一问题展开。
