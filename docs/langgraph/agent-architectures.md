# 智能体架构：从路由器到多智能体

上一篇把 State / Node / Edge 讲完了，这一篇聊聊"用它们能搭出什么形状"。
官方文档管这个叫 *Agent Architectures*，我把它当成一份**选型清单**来读。

## 先给 Agent 下个定义

文档里的定义我觉得挺干净的：

> **Agent 是使用 LLM 来决定应用程序控制流的系统。**

关键词是"控制流"。对比一下：

- **RAG**：检索 → 拼提示词 → 调模型。控制流是**写死的**，模型没得选。
- **Agent**：模型自己决定——走 A 还是走 B？调哪个工具？现在的答案够不够，要不要再查一轮？

LLM 控制权从小到大，大致是这么一条谱系：

```text
路由器（选一次）  →  工具调用 Agent（循环选多次）  →  自定义架构 / 多智能体
```

## 一、路由器（Router）

最轻量的形态：LLM 从一组**预定义选项**里挑一个。

典型场景：用户问题进来，判断是"查订单"还是"转人工"；或者判断该查数据库还是该联网搜索。

它为什么必须要"结构化输出"？因为 LLM 说完话，你的程序得**能可靠地解析出它到底选了哪个**。
三种实现方式：

1. **提示工程**：在提示词里规定格式，再自己解析（最容易翻车）。
2. **输出解析器**：调模型后用解析器从文本里抠结构化数据。
3. **工具调用 / structured output**：让模型直接吐出符合 schema 的结果（最稳）。

**什么时候够用**：流程分叉点少、每次只做一次选择。
**什么时候不够**：需要连续决策、需要模型自己调工具。

## 二、工具调用 Agent（ReAct）

路由器只能做一次决策。工具调用 Agent 把它扩展成**多步决策 + 工具访问**。

ReAct 把三件事揉在了一起：

| 概念 | 干什么 |
| --- | --- |
| **工具调用** | 模型按需选择并使用各种工具，跟外部系统交互 |
| **记忆** | 跨步骤保留信息（短期=状态里的消息历史，长期=Store） |
| **规划** | LLM 在一个 while 循环里反复决策，形成多步计划 |

执行流程其实就是上一篇那张图的循环形态：

```text
        ┌──────────────────────────┐
        ▼                          │
   LLM 决定调哪些工具 ──有工具──→ 执行工具，结果作为观察写回 messages
        │
      没有工具了
        ▼
      输出答案
```

文档里那句描述我很喜欢："当代理认为信息已经足够、不值得再调工具时，while 循环终止。"

::: tip 关于"规划"
官方讲规划时其实很朴素——不是什么高深的 planner 模块，
就是"LLM 在循环里每一步决定调什么工具、入参是什么，直到觉得够了"。
别被词吓到。
:::

预构建的 `create_react_agent` 就是这个架构的现成实现（[快速上手那篇](/langgraph/quickstart)用的就是它）。

### 工具调用本身

```python
model.bind_tools([my_function])
```

就这么一行。把任意 Python 函数绑上去，模型就知道它的入参 schema，
会根据用户自然语言决定要不要调、怎么填参。LangGraph 里工具可以用 `@tool` 装饰器，
也可以就是普通函数 + docstring。

## 三、自定义架构

路由器和 ReAct 是"通用款"，但很多时候**针对任务定制的架构效果更好**。
LangGraph 给了四个积木：

### 1. 人机协作（Human-in-the-loop）

敏感操作让人把关：批准特定动作、提供反馈改状态、在复杂决策里给指导。
完全自动化不可行或不该自动化的场景，这个模式就是刚需。
细节见[人机协作与流式输出](/langgraph/hil-streaming)。

### 2. 并行化

用 `Send` API 实现 MapReduce：并发处理多个状态、高效跑独立子任务。
上一篇讲过，这里不再重复。

### 3. 子图（Subgraphs）

复杂架构必备：每个 Agent 自己一张图（子图），状态相互隔离，
通过**状态模式里的重叠键**跟父图通信。

好处很实在：

- 单个 Agent 的状态管理是隔离的，不会互相污染；
- Agent 团队可以分层组织；
- 每个子图可以用**不同的状态模式**（搜索 Agent 只需要 query 和 docs，
  写代码 Agent 需要完全另一套）。

### 4. 反思（Reflection）

让 Agent 自己检查一遍再交付：

1. 评估任务完成度和正确性；
2. 拿反馈迭代改进；
3. 实现自我纠正。

不一定非得用 LLM 判断——**确定性方法也行**。
文档举的例子特别好：代码生成任务里，**编译报错就是反馈**，不需要再问一次模型"你觉得写得对吗"。

## 四、多智能体（Multi-agent）

什么时候该拆成多个 Agent？文档给的三个信号：

- 工具太多了，模型选工具时决策质量下降；
- 上下文太复杂，单个 Agent 追不过来；
- 系统需要多个专业领域（规划师、研究员、数学专家……）。

拆分的收益：**模块化**（好开发好测试）、**专业化**（专家 Agent 性能更好）、
**控制力**（你显式决定 Agent 之间怎么通信，而不是指望函数调用自己搞定）。

### 交接（Handoffs）：多智能体的核心原语

> 一个 Agent 把控制权**移交给**另一个 Agent。

交接要指定两样东西：

- **目标**：去哪个节点；
- **载荷**：带什么信息过去（状态更新）。

在 LangGraph 里用 `Command` 实现——上一篇说的"同时改状态+跳转"，正好是这个场景：

```python
from typing import Literal
from langgraph.types import Command

def agent(state) -> Command[Literal["agent", "another_agent"]]:
    goto = get_next_agent(...)          # 路由依据可以是 LLM 调用/结构化输出/任何逻辑
    return Command(
        goto=goto,
        update={"my_state_key": "my_state_value"},
    )
```

还有一种更隐蔽的写法：**把交接包装成工具**。这样交接就藏在工具调用里，
对工具调用型 Agent 来说最自然：

```python
from langchain_core.tools import tool

def transfer_to_bob():
    """Transfer to bob."""
    return Command(
        goto="bob",
        update={"my_state_key": "my_state_value"},
        graph=Command.PARENT,   # bob 在父图里
    )
```

### 四种拓扑

```text
网络 Network          主管 Supervisor        分层 Hierarchical       自定义 Workflow
A ↔ B ↔ C            S → A/B/C → S         顶层 S → 团队 S → 队员   固定顺序 A → B → C
每个都能路由到别人     主管决定叫谁           主管的主管               部分确定 + 部分动态
```

**网络**：每个 Agent 都能跟所有其他 Agent 通信，任何 Agent 都能决定下一步叫谁。
适合没有明确层次的问题。

**主管**：加一个主管节点，由它决定下一个叫谁。最常用，也最好理解。

```python
def supervisor(state: MessagesState) -> Command[Literal["agent_1", "agent_2", END]]:
    response = model.invoke(...)
    return Command(goto=response["next_agent"])
```

**主管（工具调用）**：主管的特例——把每个子 Agent 直接做成一个**工具**，
让支持工具调用的主管模型去调。代码量最少：

```python
supervisor = create_react_agent(model, tools=[agent_1, agent_2])
```

**分层**：主管带不动一堆 Agent 了（这正是当初逼你搞多智能体的同一个问题，又回来了），
就组队，再给团队配主管，最上面放一个顶层主管。

**自定义工作流**：提前把顺序画死（普通边），只在需要的地方留给 LLM 决定（`Command`）。
这是最"确定性"的变体。

### 通信方式：共享多少上下文？

拆成多 Agent 后最头疼的问题：**Agent 之间传什么？**

两种极端：

| 策略 | 做法 | 代价 |
| --- | --- | --- |
| **共享完整思维过程** | 大家共用一个消息列表（"草稿本"） | 草稿本疯涨，需要额外的内存管理策略 |
| **只共享最终结果** | 每个 Agent 自己一个私有消息列表，只把结论交出去 | 其他 Agent 看不到推理过程，可能影响决策质量 |

Agent 多了我倾向于后者（配不同的状态模式），Agent 少、推理链短则前者更省事。

还有个细节：**消息历史里怎么表示交接**。
交接通常是 AI 消息里带一个工具调用，但大多数 LLM 供应商不接受"有工具调用却没对应工具消息"的 AI 消息。
两个选择：

1. 补一条工具消息，比如"已成功转移到 Agent X"（**大多数人选这个**）；
2. 干脆删掉那条带工具调用的 AI 消息。

另外给消息加 `name` 字段（或者手动在内容里塞 `<agent>alice</agent>`），
在长历史里能省不少辨认的功夫。

## 选型速查

| 你的情况 | 建议架构 |
| --- | --- |
| 只有几个固定分支 | 路由器 / 条件边 |
| 单 Agent，要调工具 | `create_react_agent`（ReAct） |
| 流程确定，只是步骤多 | 普通边搭的线性图 |
| 要并行跑同一件事 N 次 | `Send`（MapReduce） |
| 中间要人工确认 | `interrupt` + `Command(resume=...)` |
| 想让结果更可靠 | 加反思节点（LLM 判断或确定性校验） |
| 一个 Agent 干不过来 | 拆多 Agent，从**主管**拓扑开始 |
| 主管也开始糊涂了 | 分层（团队 + 顶层主管） |

::: tip 我的一点看法
多智能体很火，但它不是默认选项。文档自己也说，拆分是因为"工具太多、
上下文太复杂、需要多领域"——**先确认你真的撞到这些墙了再拆**。
拆早了光是通信协议就够你喝一壶。
:::

## 小结

- 路由器 = 一次选择；工具调用 Agent = 循环选择；自定义架构 = 按任务拼积木。
- 四个积木：人机协作、并行化、子图、反思。
- 多智能体的原语是 `Command` 实现的交接；拓扑选型从主管开始，撑不住再分层。
- 通信策略（共享全量 vs 只共享结果）是多智能体设计里最容易被忽略的决策。
