# 智能体架构：从路由器到多智能体

前一篇阐述了 State / Node / Edge，本篇讨论"基于三要素可以构建哪些形态"。
官方文档称之为 *Agent Architectures*，此处将其作为一份**选型清单**来解读。

## 智能体的定义

文档给出的定义较为精炼：

> **智能体是使用 LLM 来决定应用程序控制流的系统。**

关键在于"控制流"。对比而言：

- **RAG**：检索 → 拼装提示词 → 调用模型。控制流为**硬编码**，模型无选择权。
- **智能体**：由模型自行决定——走 A 还是 B？调用哪个工具？当前答案是否充分，是否需要继续检索？

按 LLM 的控制权由小到大，大致构成如下谱系：

```text
路由器（单次选择） → 工具调用型智能体（循环选择） → 自定义架构 / 多智能体
```

## 一、路由器（Router）

控制权最小的形态：LLM 从一组**预定义选项**中择其一。

典型场景：用户问题进入后，判断属于"查询订单"还是"转人工"；
或判断应查询数据库还是联网搜索。

之所以必须依赖**结构化输出**，是因为 LLM 产生文本后，
程序须能可靠地解析出其实际选择。常见实现方式有三种：

1. **提示工程**：在提示词中约定格式，再行解析（最易出错）。
2. **输出解析器**：调用模型后，由解析器从文本中提取结构化数据。
3. **工具调用 / structured output**：令模型直接输出符合 schema 的结果（最稳健）。

**适用边界**：分叉点少、每次仅作一次选择。
**不适用**：需要连续决策、需要模型自主调用工具的场景。

## 二、工具调用型智能体（ReAct）

路由器仅支持单次决策。工具调用型智能体将其扩展为**多步决策 + 工具访问**。

ReAct 整合了三项核心概念：

| 概念 | 职责 |
| --- | --- |
| **工具调用** | 按需选择并使用各类工具，与外部系统交互 |
| **记忆** | 跨步骤保留信息（短期为状态中的消息历史，长期为 Store） |
| **规划** | 在 while 循环中反复决策，形成多步计划 |

执行流程即前一篇所述循环的形态：

```text
        ┌──────────────────────────┐
        ▼                          │
   LLM 决定调用哪些工具 ──有工具──→ 执行工具，结果作为观察写回 messages
        │
     无工具调用
        ▼
      输出答案
```

文档的表述是："当代理认为信息已充分、不值得再调用任何工具时，while 循环终止。"

::: tip 关于"规划"
此处的"规划"含义较为朴素："LLM 在循环中每一步决定调用哪些工具及其入参，直至判断任务完成"，
并没有独立的 planner 模块。
:::

预构建的 `create_react_agent` 即该架构的现成实现
（[快速上手](/langgraph/quickstart)中使用的正是它）。

### 工具调用本身

```python
model.bind_tools([my_function])
```

一行即可。将任意 Python 函数绑定后，模型即获得其入参 schema，
可依据用户自然语言判断是否调用及如何填参。LangGraph 中工具可用 `@tool` 装饰器，
也可为带 docstring 的普通函数。

## 三、自定义架构

路由器与 ReAct 属于通用形态，而**针对特定任务定制的架构往往效果更佳**。
LangGraph 提供四项构件：

### 1. 人机协作（Human-in-the-loop）

对敏感操作引入人工把关：批准特定动作、提供反馈以修改状态、
在复杂决策中给予指导。当完全自动化不可行或不宜执行时，该模式为刚性需求。
详见[人机协作与流式输出](/langgraph/hil-streaming)。

### 2. 并行化

通过 `Send` API 实现 MapReduce：并发处理多个状态、高效执行独立子任务。
前一篇已有说明，此处不再展开。

### 3. 子图（Subgraphs）

复杂架构的必备手段：每个智能体各自成图（子图），状态相互隔离，
通过**状态模式中的重叠键**与父图通信。

其价值在于：

- 单个智能体的状态管理彼此隔离，避免相互污染；
- 智能体团队可分层组织；
- 各子图可采用**不同的状态模式**（搜索智能体只需 query 与 docs，
  代码生成智能体则需要完全不同的字段）。

### 4. 反思（Reflection）

交付前由智能体自查一轮：

1. 评估任务完成度与正确性；
2. 依据反馈迭代改进；
3. 实现自我纠正。

判断者不限于 LLM——**确定性方法同样可行**。
文档所举示例具有代表性：代码生成任务中，**编译错误即为反馈**，
无需再次询问模型"结果是否正确"。

## 四、多智能体（Multi-agent）

何时应拆分为多个智能体？文档给出三项信号：

- 工具数量过多，模型在选择工具时决策质量下降；
- 上下文过于复杂，单个智能体难以跟踪；
- 系统需要多个专业领域（规划、检索、数学等）。

拆分的收益为：**模块化**（便于开发与测试）、**专业化**（领域专家性能更优）、
**控制力**（通信方式由开发者显式决定，不依赖函数调用的自然结果）。

### 交接（Handoffs）：多智能体的核心原语

> 一个智能体将控制权**移交**给另一个智能体。

交接需要指定两项内容：

- **目标**：跳转至哪个节点；
- **载荷**：携带何种信息（状态更新）。

LangGraph 中以 `Command` 实现——前一篇所述"同时更新状态与跳转"正对应此场景：

```python
from typing import Literal
from langgraph.types import Command

def agent(state) -> Command[Literal["agent", "another_agent"]]:
    goto = get_next_agent(...)          # 路由依据可为 LLM 调用、结构化输出或任意逻辑
    return Command(
        goto=goto,
        update={"my_state_key": "my_state_value"},
    )
```

另一种较为隐蔽的写法：**将交接包装为工具**。
对工具调用型智能体而言，交接隐含于工具调用之中，形式最为自然：

```python
from langchain_core.tools import tool

def transfer_to_bob():
    """Transfer to bob."""
    return Command(
        goto="bob",
        update={"my_state_key": "my_state_value"},
        graph=Command.PARENT,   # bob 位于父图
    )
```

### 四种拓扑

```text
网络 Network          主管 Supervisor        分层 Hierarchical       自定义 Workflow
A ↔ B ↔ C            S → A/B/C → S         顶层 S → 团队 S → 队员   固定顺序 A → B → C
任一节点可路由到他人   主管决定调用对象        主管之主管               部分确定 + 部分动态
```

**网络**：每个智能体均可与所有其他智能体通信，任一智能体均可决定下一步调用对象。
适用于无明确层次结构的问题。

**主管**：增设一个主管节点，由其决定下一个调用对象。最为常用，也最易理解。

```python
def supervisor(state: MessagesState) -> Command[Literal["agent_1", "agent_2", END]]:
    response = model.invoke(...)
    return Command(goto=response["next_agent"])
```

**主管（工具调用）**：主管的特例——将各子智能体直接实现为**工具**，
交由支持工具调用的主管模型调用。实现成本最低：

```python
supervisor = create_react_agent(model, tools=[agent_1, agent_2])
```

**分层**：当主管无法有效管理大量智能体时（此即当初引入多智能体的同一问题再度出现），
可先组队并为团队配置主管，最上层再设顶层主管。

**自定义工作流**：预先以普通边固定执行顺序，仅在必要处交由 LLM 决策（`Command`）。
这是确定性最高的变体。

### 通信策略：共享多少上下文

拆分为多智能体后最棘手的问题是：**智能体之间传递什么？**

两种极端策略：

| 策略 | 做法 | 代价 |
| --- | --- | --- |
| **共享完整思维过程** | 共用同一消息列表（"草稿本"） | 消息列表迅速膨胀，需额外的内存管理策略 |
| **仅共享最终结果** | 各智能体持有私有消息列表，只传递结论 | 其他智能体无法获知推理过程，可能影响决策质量 |

智能体数量较多时倾向后者（配合各自独立的状态模式）；
数量少、推理链短时前者更为简便。

另一项细节：**消息历史中如何表示交接**。
交接通常表现为 AI 消息中携带工具调用，但多数 LLM 供应商不接受
"存在工具调用而无对应工具消息"的 AI 消息。两种处理方式：

1. 补充一条工具消息，例如"已成功转移到 Agent X"（**实践中多采用此方案**）；
2. 直接移除该条带工具调用的 AI 消息。

此外，为消息添加 `name` 字段（或在内容中标注智能体名称），
在较长的历史中可显著提升可辨识度。

## 选型速查

| 情况 | 建议架构 |
| --- | --- |
| 分支少且固定 | 路由器 / 条件边 |
| 单智能体、需调用工具 | `create_react_agent`（ReAct） |
| 流程确定、仅步骤较多 | 以普通边连接的线性图 |
| 需并行执行同一任务 N 次 | `Send`（MapReduce） |
| 中途需人工确认 | `interrupt` + `Command(resume=...)` |
| 需提升结果可靠性 | 增加反思节点（LLM 判断或确定性校验） |
| 单智能体已无法胜任 | 拆分为多智能体，**从主管拓扑起步** |
| 主管亦难以驾驭 | 分层（团队 + 顶层主管） |

::: tip 关于多智能体
多智能体并非默认选项。文档亦明确指出，拆分的前提是"工具过多、
上下文过复杂、需要多领域"——应先确认确实遭遇这些瓶颈。
过早拆分，仅通信协议的复杂度就足以抵消其收益。
:::

## 小结

- 路由器 = 单次选择；工具调用型智能体 = 循环选择；自定义架构 = 按任务组合构件。
- 四项构件：人机协作、并行化、子图、反思。
- 多智能体的原语是以 `Command` 实现的交接；拓扑选型从主管开始，不足时再分层。
- 通信策略（共享全量 vs 仅共享结果）是多智能体设计中最易被忽略的决策。
